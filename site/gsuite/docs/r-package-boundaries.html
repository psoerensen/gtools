R package boundaries

The R layer is divided by user task instead of placing every interface in one large gsuite package. The root gsuite package remains the ecosystem identity, website and integration surface. Independently distributed task capabilities are R/native pairs: an R package owns the user contract and its corresponding native library owns the implementation. Each task package can be installed and used without the root package.

Dependency rule

The dependency direction is:

gbase <- gcorr, glma, gbayes, gscore, gmap, gsea

task packages do not import gsuite
task packages depend on each other only for an explicit scientific workflow

gbase must not depend on a task package. It may use the installed public gmat and gbits native interfaces for the agreed task-neutral genotype-preparation contract. A task package must not depend on the root gsuite package. This prevents dependency cycles and lets users install one task without installing the complete suite.

Package map

This is the canonical map of R/native distribution units. Method details belong in the capability overview; native transitive dependencies belong in the build manifests.

What belongs in gbase

Code belongs in gbase only when it is stable, task-neutral and needed by more than one task package. The package contains or will own:

  • one-trait, allele-labelled summary-statistics data frames;
  • checkStat() mapping, harmonization and explicit QC of reported statistics against a Glist reference;
  • validation of marker identity, positions, alleles and supplied numerical columns;
  • explicit allele-oriented variant keys;
  • gbase::gprep() preparation and sparse-LD publication plus the serializable Glist contract shared by individual-level task packages;
  • summary-based marker filtering and Glist-owned LD scores, regional matrices, and complete verified regional eigensystems.

checkStat() follows the established qgg workflow and returns an ordinary data frame. Its canonical columns are rsids, chr, pos, ea, nea, with the available analysis columns among eaf, b, seb, stat, p, n and info. Downstream functions validate the subset they require. Gbase does not require a public summary-statistics class, constructor, accessor or print method.

The following do not belong in gbase:

  • automatic strand inference or downstream LD-model fitting;
  • genotype, LD or matrix storage;
  • statistical fitting, priors or sampler controls;
  • scoring, correlation or association algorithms;
  • cross-dataset permissions and disclosure policy;
  • orchestration across tasks.

Those responsibilities remain with gmat/data preparation, the relevant task package, gshare, or the gsuite umbrella.

Low-level native libraries do not automatically require user-facing R packages. In particular, gbits remains an implementation dependency unless a distinct user task emerges.

Present native dependency closures

These are planning boundaries, not new build declarations:

R package Main native dependencies
gbase gmat and gbits for genotype/sparse-LD preparation and LD utilities; gsolve for complete verified regional eigensystems
gcorr gcorr, with prepared gmat LD resources
gscore core gscore for BED application plus gscore::summary for C+T; the installed summary library currently brings gbayes, gmat, gsolve and gbits transitively
gbayes gbayes, gmat, gbits and gsolve; no CHOLMOD, MKL, PARDISO or OpenMP runtime in the qualified portable profile
glma glma, with gmat/gbits, greml or gbayes where the selected association task requires them
gmap unified gmap library and gbayes, with prepared gmat resources
gsea gsea and its selected gbayes companion

Each package build verifies its installed dependency closure.

Summary-statistics integration

gbase::checkStat() maps, validates, harmonizes and filters ordinary qgg-style data frames. Analysis packages then validate the exact columns they consume.

gsuite is in private development. gsim and gact are public.
