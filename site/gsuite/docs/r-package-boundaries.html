R package boundaries

The R layer will be divided by user task instead of continuing to place every interface in one large gsuite package. The root gsuite package remains the umbrella: it connects tasks, checks compatible component versions and provides suite-wide guidance. Each task package can also be installed and used alone.

This document defines the first boundary. It does not move existing functions or change their current behaviour.

Dependency rule

The dependency direction is:

gbase
  ├─ gcorr, gscore, gbayes, glma, gmap, gsea, greml, gmat, gshare, ...
  └─ task packages do not depend on each other unless the scientific task requires it

task packages
  └─ gsuite umbrella

gbase must not depend on a task package. A task package must not depend on the root gsuite package. This prevents dependency cycles and lets users install one task without installing the complete suite.

What belongs in gbase

Code belongs in gbase only when it is stable, task-neutral and needed by more than one task package. The initial package contains:

  • one-trait, allele-labelled summary statistics;
  • validation of marker identity, positions, alleles, sample counts and the two supported numerical forms;
  • extraction of values and provenance;
  • explicit allele-oriented variant keys.

The initial object accepts either effect plus standard error or score plus information. Optional marker sample count, p-value and allele frequency remain part of the common data. The object records response units, analysis model and provenance without claiming that those declarations are true.

The following do not belong in gbase:

  • allele alignment, strand inference or LD preparation;
  • genotype, LD or matrix storage;
  • statistical fitting, priors or sampler controls;
  • scoring, correlation or association algorithms;
  • cross-dataset permissions and disclosure policy;
  • orchestration across tasks.

Those responsibilities remain with gmat/data preparation, the relevant task package, gshare, or the gsuite umbrella.

Current gsuite exports and intended owners

The groups below cover the current exported interface. S3 methods move with the class or generic they serve.

gscore() and score fit/prediction methods gscore

gsea() and enrichment-result methods gsea
greml(), persistent mixed-model, pedigree, multivariate, longitudinal and component-model constructors and methods greml
gsolve(), gsuite_solve() and solver result methods gsolve-facing package or an internal greml dependency, to be decided from direct user demand
Current gshare*, read and write wrappers Provisional implementations; replace only after the single public gshare R interface is designed

Low-level native libraries do not automatically require user-facing R packages. In particular, gbits remains an implementation dependency unless a distinct user task emerges.

Present native dependency closures

These are planning boundaries, not new build declarations:

Proposed R package Main native dependencies
gbase none
gmat-facing preparation gmat, gbits and selected gsolve adapters
gcorr gcorr, with prepared gmat LD resources
gscore gscore, with gmat/gbits resources
gbayes gbayes, with gmat/gbits and gsolve dependencies used by its public routes
glma glma, with gmat/gbits, greml or gbayes where the selected association task requires them
gmap gmap and gbayes, with prepared gmat resources
gsea gsea and its selected gbayes companion
greml greml, gsolve, gmat and gbits as required by the fitted model
gshare gshare protocol library; statistical dependencies should reduce as task implementations move to their owners

Each extraction must confirm its exact installed dependency closure before a package DESCRIPTION is finalized.

Summary-statistics audit

The current sumstat() performs useful task-specific preparation, but its returned object cannot yet be converted losslessly to the common contract:

  • the Z-alignment route returns marker, alleles, Z and sample count, but omits chromosome and position;
  • the standardization route returns standardized effect, sample count and p-value, but no longer retains the reported effect, standard error or coordinates;
  • response units and the analysis-model description are not stored;
  • LD-reference provenance and portable study provenance are currently combined.

For that reason, this milestone does not make the root package import gbase or silently manufacture missing fields. The next integration change should retain the reported, aligned values and coordinates during preparation, then construct a gbase object explicitly.

First package and boundary demonstration

The independently buildable package is under packages/gbase/. Its focused test constructs one common effect/standard-error object and maps it to two separate adapter inputs:

  • an exchange payload retaining effects, uncertainty, coordinates and alleles;
  • a correlation input deriving Z while retaining marker and allele order.

The demonstration deliberately does not place those adapters in gbase. Actual gshare and gcorr adapters belong in their respective packages and are the next vertical integration milestone.

Extraction order

  1. Make sumstat() retain enough checked information to construct the common object without inference or loss.
  2. Add the gshare exchange adapter and gcorr consumer adapter in their owners.
  3. Extract gcorr as the first task package and keep the root gsuite workflow working against it.
  4. Extract gscore, then gbayes and the remaining task packages based on their verified dependency closures.
  5. Keep Python implementation deferred; later Python interfaces should mirror these task and data contracts rather than the historical R file layout.

gsuite is in private development. gsim and gact are public.
