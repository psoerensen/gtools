Standalone mixed models with YAML

Install the Linux command, specify a complete model and inspect predictions, timings and memory.

One YAML file specifies input files, column bindings, the statistical model, natural covariance matrices, fitting controls, threads and requested outputs. The interface uses schema: gsuite.model/v1-draft. Unknown keys and unsupported combinations are rejected; there are no legacy syntax aliases. Existing R interfaces are unchanged.

Linux build and run commands handle the private MKL ILP64/SuiteSparse library paths and disable OpenMP affinity binding automatically. Slurm retains the CPU allocation and YAML controls the native thread requests. No manual linker or affinity exports are needed; per-fit run.json records the execution environment.

Installation

The standalone command is gsuite. Its Python frontend prepares inputs and labels results; greml/gsolve and the genotype libraries perform the numerical work. R is not required. The existing R interfaces remain separate.

The command is the same for every currently supported mixed-model route: analysis.task selects supplied-covariance solving or REML. This interface does not imply standalone support for every other gsuite analysis package. New bundles install only gsuite, with no greml command alias. The native mixed-model driver and libraries retain their greml/gsolve component names.

The GenomeDK Linux x86-64 binary installer has a recorded successful validation under its earlier command name. The renamed command requires a refreshed bundle and fresh installer qualification; the earlier accepted archive is not modified. Binary archives remain private validation artifacts; this website does not provide a public binary download. Use an archive and matching checksum supplied by the maintainer. An existing Conda or Mamba installation and network access to its runtime packages are needed.

On HPC, use an allocated compute-node shell with $TMPDIR available. Start the installer with Python 3.10 or newer; a small bootstrap environment suffices:

conda create -n gsuite-installer -c conda-forge python=3.12 -y
conda activate gsuite-installer

Set ARCHIVE to the absolute path of the supplied archive. The checksum file must be beside it. Choose a new prefix at its final installation location:

(
set -euo pipefail
ARCHIVE=/path/to/gsuite-genomedk-BUILD.tar.gz
PREFIX="$HOME/software/gsuite"
: "${TMPDIR:?Run inside a Slurm compute-node allocation}"

cd "$(dirname "$ARCHIVE")"
sha256sum -c "$(basename "$ARCHIVE").sha256"
WORK=$(mktemp -d "$TMPDIR/greml-install.XXXXXX")
tar -xzf "$ARCHIVE" -C "$WORK"

bash "$WORK/$(basename "$ARCHIVE" .tar.gz)/install.sh" \
  --prefix "$PREFIX" --scratch-directory "$WORK"
)

The installer creates <prefix>/runtime and <prefix>/app, installs pinned runtime packages, checks library resolution and runs the small numerical campaign. No compiler, R, CMake or development headers are requested. An existing prefix is preserved rather than overwritten. Receipts and copied test results remain under <prefix>/installation.json and <prefix>/validation/. Do not move the installed Conda prefix; install again at a new final location when needed. The temporary extraction directory is not needed for later fits.

Add the command to PATH in each new shell:

export PATH="$HOME/software/gsuite/bin:$PATH"
gsuite validate /path/to/model.yml
gsuite describe /path/to/model.yml
gsuite run /path/to/model.yml

The installed launcher selects its private runtime. It does not require activating gsuite-installer for subsequent fits. For a first test, copy the included small dataset to a writable working directory:

cp -a "$HOME/software/gsuite/app/example" ./example
gsuite run example/model.yml

The example includes CSV pedigree/phenotypes, SNP-major PLINK BED/BIM/FAM and simulated true genetic values. Truth is not used by the fit. Its eight phenotype rows and two traits are a workflow check, not prediction-accuracy evidence.

The models/ directory contains 42 self-contained YAML examples and their tiny inputs. The external-data 1M production recipe is separately preserved under recipes/model-1m-ancestral-t16.yml in the binary distribution. Copy it to your work directory and edit its input/output paths before use. No large dataset is included or required by installation checks. YAML files and data travel together; relative paths resolve beside the YAML, not beside the executable.

Inspect and run

From an extracted source bundle after bash build.sh:

export PATH="$PWD/install/bin:$PATH"
gsuite validate example/model.yml
gsuite describe example/model.yml
gsuite run example/model.yml

From a checkout, the same commands use python tools/build/hpc_single_step/gsuite.py and an explicit --exe /path/to/greml_single_step_evaluate. Omit --output to use output.directory. Input and output paths in YAML resolve beside that YAML. The final result directory must be fresh. Source inputs are never rewritten.

validate checks the model and input tables without calling the native driver; it is not a numerical reference campaign. describe additionally prints expanded dimensions, channel order, parameter coordinates and execution settings without fitting. It reads input tables and genotype metadata. run chooses the equations and task from the YAML, including supplied-covariance solving or REML, without model-specific commands.

Scratch, results and resource reports

The runner creates a private working directory under $TMPDIR, or the system temporary directory when $TMPDIR is unset. --scratch-directory /existing/path selects another parent. SQLite snapshots use this scratch by default; an explicit YAML execution.preparation.directory remains honored. No RAM ceiling or run timeout is imposed. Slurm allocation and environment activation remain setup steps.

The original YAML remains the base for resolving inputs, even when run from another directory. Prepared inputs, native work and labelled output are written in scratch, then collected into output.directory (or --output). The runner reserves the destination exclusively, so another invocation cannot overwrite it. Successful collection removes only this invocation’s scratch. Failed fits also collect diagnostics and exit nonzero. If copying fails, scratch is retained and its recovery path is printed; the final directory may contain a partial copy.

The result directory contains the existing native/CSV outputs and run.json, plus inputs/, a byte-preserved model.yml snapshot, console.log, worker.json and execution.json. The snapshot keeps the original YAML syntax and relative paths; execution.json.model_path identifies their original resolution base. Copied inputs and native reports preserve recorded execution paths, not a restart contract for prepared fits.

execution.json reports preparation, fitting, native preparation/evaluation, Python output formatting, result collection and total elapsed time. Native phase timings, iteration counts and residual gates remain in run.json. Memory reports distinguish native peak RSS from sampled aggregate RSS of the coordinator, Python worker and native descendants. Aggregate RSS can count shared pages more than once, and brief peaks between samples can be missed; it is not Slurm/cgroup accounting. Unsupported sampling is reported as unavailable rather than zero.

For example, after copying the 1M production recipe to model-1m.yml and editing its input/output paths:

gsuite run model-1m.yml

Execution and estimation controls belong in YAML. --exe selects the native program; --output changes only the destination.

Input and model sections

Section Meaning
traits Ordered response/channel names, also used for environments
inputs All CSV/TSV, PLINK, covariance, assignment and prediction-grid files
relationships Named pedigree, single-step, APY or supplied relationship models
bases Optional power, Legendre or Chebyshev regression bases
covariances Natural variances/covariances or FA loadings and specific variances
model Observation input, fixed formula, named random effects and residual structure
analysis task: solve for supplied covariances, or task: reml for estimation
execution Formulation, solver, factorization, threads and linear-solve tolerances
output Destination, selected coefficient tables, predictions and optional uncertainty

Matrices are covariances, never inverses. Inline matrices use one YAML list item per row, for example - [1.0, 0.2]. Their order follows the generated channels; labelled inline or external matrices must match that order exactly. Matrices must be finite, symmetric and positive definite. Under REML they are starting values; otherwise they are fixed supplied values.

Column bindings use neutral logical names such as individual, parent1, parent2, mother, time or environment. IDs remain strings, including leading zeros. Wide phenotypes map trait names to response columns. Long phenotypes use layout: long and responses: {trait: trait_column, value: value_column}. One record ID is one residual occasion: ID/trait pairs must be unique and mapped covariates must agree within an ID. Distinct visits need distinct record IDs. Absent trait rows are missing responses, without imputation. Independent prediction grids remain wide.

Complete ssSNPBLUP example

Save this as model.yml beside the supplied example’s phenotypes.csv, pedigree.csv and genotypes.bed/.bim/.fam. The physical columns in this synthetic example use animal, sire and dam; the logical bindings remain individual, parent1 and parent2 for plant, human and animal datasets. Edit the physical bindings for another dataset. The matrices below are covariances on their natural scale, in the declared [milk, fat] trait order. The example requests eight threads for marker work and one for other phases; request at least eight Slurm CPUs, or edit the YAML to match your allocation.

# Tiny synthetic example: covariance matrices follow [milk, fat].
schema: gsuite.model/v1-draft
name: single_step_example
traits: [milk, fat]
inputs:
  observations:
    type: table
    file: phenotypes.csv
    id: record_id
    columns: {individual: animal, site: herd, age: age}
    responses: {milk: milk, fat: fat}
  pedigree:
    type: pedigree
    file: pedigree.csv
    columns: {individual: animal, parent1: sire, parent2: dam}
  genotypes: {type: plink, prefix: genotypes, id: IID}
relationships:
  A: {type: pedigree, input: pedigree}
  H:
    type: single_step
    pedigree: A
    genotypes: genotypes
    genomic: {adjustment: none, polygenic_weight: 0.0, independent_ridge: 0.05}
covariances:
  genetic:
    - [1.0, 0.1]
    - [0.1, 0.04]
  individual_environment:
    - [0.4, 0.02]
    - [0.02, 0.02]
  residual:
    - [2.0, 0.08]
    - [0.08, 0.05]
model:
  data: observations
  fixed: "factor(site) + age"
  random:
    genetic: {group: individual, relationship: H, covariance: genetic}
    individual_environment: {group: individual, covariance: individual_environment}
  residual: residual
analysis: {task: solve}
execution:
  formulation: ss_snp
  solver: pcg
  sparse_backend: pardiso
  preconditioner: qnn_reuse
  pedigree_factorization: ancestral_sweeps
  convergence: {relative_tolerance: 1.0e-10, maximum_iterations: 4000}
  threads: {default: 1, marker_products: 8, marker_setup: 8}
output:
  directory: ../results/example
  predictions:
    genetic_values: {effects: [genetic], levels: all}

Then use the same command as for every other supported model:

gsuite run model.yml

This supplied-covariance model selects packed PCG, exact ancestral pedigree sweeps and Qnn reuse. Change model/task declarations in YAML rather than choosing a different executable. The model specification gives the full syntax for other effects and covariance families.

Solver and threads

For fast packed ssSNPBLUP:

execution:
  formulation: ss_snp
  solver: pcg
  sparse_backend: pardiso
  pedigree_factorization: ancestral_sweeps
  preconditioner: qnn_reuse
  threads: 16

A scalar sets every applicable thread request. Override particular operations with threads: {default: 16, decode: 4}. Packed controls are marker_products, marker_setup, decode, pedigree, preconditioner and vectors. Compiled models use factor and relationship; raw-genotype APY also uses decode and genomic_products. A mapping without default uses one for unspecified operations. Request matching Slurm CPUs. Thread settings are phase-specific requests: Python preparation and dependency-ordered pedigree work can be serial.

ancestral_sweeps preserves the full statistical model with a smaller retained pedigree factor and exact peripheral sweeps, including supplied metafounders. full_qnn is available for comparison and is the default. qnn_reuse avoids a second global pedigree factor; shifted_pedigree is the alternative packed preconditioner. Linear PCG tolerances belong in execution.convergence. Ordinary compiled models support direct or PCG solving. Exact/APY ssGBLUP uses compiled PCG and formulation: ss_gblup.

Covariance estimation

analysis.estimate selects free covariance blocks; omitted blocks stay fixed. Sparse-direct compiled REML supports unstructured and FA covariance and scalar or separable multivariate serial parameters. Natural starts are transformed internally. analysis.constraints can fix named optimizer coordinates; describe lists them. A fixed Cholesky coordinate is not a fixed covariance entry. Direct optimizer controls include maximum_step and maximum_line_search_reductions.

Packed EM-REML estimates unstructured genetic and independent residual covariance for ordinary pedigrees, with one genetic channel per trait and fixed additional identity-effect covariances. Its update control is optimizer.step_fraction in (0, 1]. Score traces have their own explicit solve and precision budgets under analysis.traces. Exact traces are small references; stochastic traces require explicit probes, seed, total solve cap and maximum score MCSE. Stochastic convergence also requires an independent final score check. See packed REML controls and limits.

Omit analysis.likelihood to skip global determinant work in packed REML. Optional method: exact requires maximum_dimension; method: slq requires maximum_operator_products, with optional probe/depth/precision controls. It reports the likelihood change from the start to the final covariance state, with separate sampling MCSE and Lanczos-depth sensitivity. It does not control EM updates or certify a global optimum. Unqualified optional likelihood does not reject an otherwise qualified point fit. Compiled direct REML retains its absolute likelihood and line-search acceptance.

Model capabilities and limits

The complete examples cover pedigree, packed ssSNPBLUP, exact/APY ssGBLUP, direct/maternal and weighted incidence, regression, external relationships, groups/metafounders, FA, serial residuals and estimation. The specification gives exact syntax and route-specific supported combinations.

Supplied FA uses natural loadings and specific variances with an identified triangular leading loading block; it reduces covariance parameters, not genetic coefficient count. Serial models support scalar or separable trait-by-time AR1 and exponential covariance with actual gaps and missing traits. Compiled models also accept general finite trait-by-visit covariance blocks.

Fixed/random groups, explicit phantom group-parent absorption, combined bases and supplied/estimated Gamma are distinct statistical declarations. Packed ordinary random groups use implicit sweeps; packed fixed/combined groups prepare ordinary inheritance columns once, requiring O(individuals × groups) storage. Metafounders retain every correlated latent base. Gamma pseudo-EM requires an explicit absolute marker base and is separate from joint REML.

Sparse external natural covariance uses a retained sparse inverse-action factor; fill and exact precision-diagonal setup can be costly. Raw PLINK APY uses an explicit ordered core and bounded tiles/file-backed cross products. Industrial APY preparation remains unqualified. Packed REML currently excludes FA, serial/grouped residuals, groups/metafounders and joint PEV requests.

Existing selected exact/stochastic PEV options remain conditional on supplied covariances, with explicit work budgets and separate qualification. Their precision is not improved by this interface cleanup. The model-only validator skips uncertainty cases.

Outputs, resources and validation

Every fit writes run.json, checksums, logs, native diagnostics and requested prediction CSVs. Standard coefficient tables are fixed_effects.csv and random_effects.csv. REML adds variance_components.csv, parameters.csv, reml_history.csv, convergence.json and likelihood.json. The latter reports scale, method, status and the value/error/work diagnostics available for that route. Read acceptance/convergence flags before using estimates. Failed covariance fits retain diagnostic states/history but publish no qualified prediction tables.

Timings and peak RSS in native metrics describe the native process; they exclude Python preparation. Tables, long-row grouping and prediction grids are spooled to temporary SQLite storage. Optional execution.preparation.directory selects an existing scratch parent. A fresh child is removed on normal completion or handled failure. Pedigree/effect indexes, genotype metadata, supplied matrices and native factors still require memory. There is no application RAM ceiling, admission guard or timeout.

After building a source bundle, run python3 test_example.py --output results/example-check for the complete small data/truth workflow, or python3 validate.py --output results/model-validation for the independent small-reference campaign and non-uncertainty examples. Validation receipts record actual case counts and hashes; tiny references do not qualify industrial runtime, memory or stochastic precision. For bundles containing the existing 50K fixture, see validation50k/README.md for separate explicit runs. No large dataset or remote job is run automatically.
