Architecture

Responsibilities, dependencies and representative workflows across gsuite libraries.

The public R surface groups preparation under gprep(), gfilter(), ldprep() and sumstat(). Covariance preparation and SEM/GGM share gcorr(); regional fitting and colocalisation share gmap(). Native method ownership and result classes remain distinct. sumstat() prepares summary inputs; gstat() tests marker sets through native glma and supplies evidence for gsea.

Purpose

gsuite is the unified interface to a modular family of independently versioned computational libraries. Each native library owns a narrow data, numerical, or statistical boundary and remains independently buildable. The current gsuite R package integrates and packages selected native capabilities. A future Python interface is intended to share the same model/task contracts and native APIs; no Python implementation is present yet. The R package exposes the public combinations recorded in the authoritative capability overview, with LMM combinations in the model catalog; it is not necessarily a binding for every native entry point.

gsuite and gsim are the user-facing R packages. gsim generates genotype, pedigree and observation data; gsuite provides analysis interfaces. The tutorial connects them through ordinary R data frames.

Responsibilities

Library Responsibility Immediate boundary
gbits Packed genotype storage, PLINK BED access, selections, transformations, genotype products, and weighted covariance/normal operators Does not own genomic resource metadata, general solvers, or statistical models
gmat BED/BIM/FAM resources, ordered panels, sparse-LD construction and storage, sparse-LD algebra, and LD scores Delegates BED decoding to gbits and does not fit LD-score regressions
gsolve Model-independent operators, factorizations, eigensystems, selected inversion, preconditioned conjugate gradient, probes, stochastic log determinants and shared positive quadratic-tail approximation Contains no genotype, likelihood, or mixed-model semantics; integrates external sparse factorization backends
greml ML/REML covariance models, exact and stochastic inference, sparse mixed-model equations, optimization, prediction, and uncertainty Uses gsolve for numerical primitives and does not own genotype formats
gcorr LDSC, GNOVA, SumHer, HESS/rho-HESS, SUPERGNOVA, LAVA, HDL-L; covariance-summary SEM/GGM and prepared-instrument MR Consumes gmat LD resources and gsolve numerics; colocalisation belongs in gmap
gscore Multi-score BED application, scoring-specific weight construction/selection and prepared prediction targets Core scoring remains standalone; optional gscore::summary reuses gbayes inference. gsuite binds selected posterior prediction and a standalone gscore() fit/select/apply interface
gsim User-facing R simulation of genotypes, pedigrees and observation records Owns simulation workflows; generated data can be used in gsuite analyses
glma Native linear, binary logistic and Gaussian mixed/LOCO association plus prior-selected LOCO fitting, structure checks, calibration, offset testing and prepared summary-statistic gene evidence/ACAT Uses installed gmat/gbits, greml and gbayes; gsuite exposes binary and quantitative-trait routes through glma(), sharing genotype reads for multiple exact linear traits and immutable preparation for LOCO traits
gmap Native colocalisation, regional Bayesian analysis and posterior-set interpretation Core is standalone; optional gmap::bayes uses gbayes; gsuite binds regional Bayesian fitting, ABF and component colocalisation
gbayes Native Bayesian regression and single-/multi-effect inference Uses gmat cross-products or prepared factors; single-/multivariate summary regression through gsuite::gbayes and regional inference through gsuite::gmap
gsea Native gene-set and genomic-feature enrichment: prepared sets, aggregate statistics, over-representation, resampling, preranked GSEA, competitive GLS, MAGMA-route summary preprocessing and scalar/multitrait Bayesian pathways Reuses gsolve factors; optional gsea::bayes shares pathway preparation and delegates scalar/multitrait BayesC/BayesR inference to gbayes. gstat() supplies separate gene evidence; gsea() exposes set-based ORA, preranked, competitive, bounded MAGMA and Bayesian workflows. Association belongs in glma; LDSC/SumHer enrichment remains in gcorr
gsuite Unified R/native entry point and suite-level integration documentation Binds selected gsolve, greml, gbits, gmat, gcorr, glma, gscore and gmap/gbayes capabilities and requires the gbits gsolve adapter

The summary preparation and scoring workflow keeps allele preparation separate from estimation. gscore owns score selection and application; additional gbayes engines return posterior quantities directly. GNOVA conditional summaries reuse saved category covariance and paired deletes.

How the R interface connects the components

The pedigree data-frame workflow normalizes short covariance specifications and explicit gvc() components into one internal model description. Formulas define fixed and random bases, variables bind record IDs, kernels define relationships, covariance descriptors declare coordinates and optional starts. greml() estimates variance components; gsolve() solves at supplied values or takes a prepared formula fit directly. gfit() retains its task-based interface. The shared R preparation and result classes avoid duplicating statistical or numerical implementations.

The R name gsolve() describes a user task: solve an LMM. Model assembly and covariance meaning still belong to native greml; numerical solving remains in native gsolve. A fit stores ordinary prepared R data for a later solve, not a persistent native factor. See the interface contract. The adapter owns R validation, sparse fixed-design construction and result labels; it calls the existing specialized pedigree interfaces or the public component-LMM constructors and fitters for independent groups of random intercepts. A named vector of grouping columns in one gvc() declares correlated channels sharing a pedigree or identity relationship; separate descriptors remain independent. Residual group, structure, block and time fields bind data columns to existing grouped, AR(1) and exponential component residual constructors. Missing-response filtering is shared by phenotypes, incidence and residual metadata. No new native numerical implementation or dense relationship matrix is introduced. formula and formulas are equivalent; supplied starts do not select a different route. An explicit gs_fit_control() object selects the specialized compiled interface. General sparse-direct defaults use CHOLMOD selected inversion; independent components reuse gs_lmm_control().

For gprep(task = "prepare"), ownership is fixed as follows:

Responsibility Owner
Public R interface, orchestration, serializable descriptor gsuite
BED validation and packed genotype counts gbits
BIM/FAM parsing, identity, metadata, and file alignment gmat
Persistent genotype representation Existing PLINK BED
Behavioural and scientific comparison Read-only qgg

For gprep(task = "sparseld"), gsuite validates the Glist and orchestrates selection; gmat owns sparse-LD calculation, its disk CSR, validation, and LD scores; gbits remains the packed BED path; existing BED remains the genotype store; and unchanged qgg and sblr are behavioural and consumer references.

The independent LDlist interface reuses gmat’s existing SparseLdDiskResource and native disk inspection. ldprep(Glist, reference) creates an R descriptor without copying LD files; validate_LDlist() reopens and checks it without requiring genotype inputs. gmat owns the native resource, while gsuite owns R labels, serialization and validation orchestration. No new native storage format is introduced. LD computation is delegated to the existing sparse-LD preparation route; named score preparation delegates ordinary and partitioned/corrected calculations to gmat. gsuite stores definitions and validates saved-score compatibility. Regional dense extraction belongs to gmat and reuses its streaming disk parser. gsolve supplies the full eigensystem and numerical diagnostics; gsuite binds these installed public APIs and stores reusable region caches. gmat has no new gsolve dependency. All R/Rcpp code remains in gsuite. See LD references.

gcorr now provides native adapters for these LD resources and an immutable PreparedRegionalLd shared by HESS, rho-HESS, SUPERGNOVA, LAVA and HDL-L. gsolve verifies imported full eigensystems once; subsequent native fits reuse them while applying their own statistical component selection. The gcorr() R interface now connects these resources to ordinary/partitioned LDSC and GNOVA, independent and joint-region HESS/rho-HESS, continuous-trait LAVA point estimates, univariate tests and optional bivariate simulation inference, HDL-L local likelihood and SUPERGNOVA covariance. See the summary-statistic tutorial for its bounded scope.

Across these methods, result tables use explicit reference, region, annotation-category and architecture-component labels. Named h2/cov/rg matrices share one layout; method-specific uncertainty, native diagnostics and inconsistent pairwise estimates remain visible. See result conventions.

The common gcorr() interface also exposes SumHer architecture-component and reference-total h2/cov/rg. Multiple traits use the native coordinated marginal and pairwise fits, with joint fixed-weight jackknife covariance when blocks are supplied. Tagging weights are explicit and separate from architecture-weighted scores; no cross-ancestry or full upstream-software parity is implied.

Regional LAVA also accepts explicit binary-trait metadata, reusing LDlist allele frequencies for native logistic-Wald reconstruction. Observed and liability h2 remain distinct; binary/mixed pairs use the existing screening and optional bivariate simulation inference. LAVA shares each regional fit across traits and exposes partial correlations, multiple regression, explained variance and supported conditional/omnibus inference.

Native regional request lists now resolve explicitly named references and regions, reuse prepared LD, and retain labelled results or per-request errors. Joint HESS also accepts prepared regions. These are sequential native calls; every trait within a model must select the same reference, with no cross-ancestry estimator implied by the reference labels.

Dependencies

CHOLMOD/SuiteSparse and PARDISO supply external factorization and solve backends. The gsolve selected-inverse implementation reuses CHOLMOD supernodal factors; it is distinct from those external libraries and does not use PARDISO for selected inversion. Other dense and iterative routes remain available.

Building gbits::gsolve_adapter is optional for gbits; when built, the adapter requires both gbits and gsolve. The current gsuite build requires the adapter. There is no reverse dependency from gsolve or greml to gbits. The gscore scoring implementation reads BED directly and has no suite-library dependency. Its optional summary companion depends on gbayes, gmat, gsolve and gbits and is now a gsuite runtime dependency for posterior prediction. gsim is a separate user-facing R package; its simulation-to-analysis workflow exchanges data with gsuite and is not a native-library dependency. gbayes is a native library using gmat and gsolve. gmap retains standalone colocalisation and provides an optional gmap::bayes companion for regional posterior workflows. Both are now installed dependencies of the experimental gsuite gmap() R interface. Only the R conversion layer lives in gsuite; fitting and posterior-set construction remain native. The R interface accepts named regions and traits, with explicit sufficient statistics and optional native parameter learning. Residual learning requires complete in-sample LD and explicit phenotype normalization. Each region is prepared once across traits, using verified cached eigenpairs when available. Traits are fitted separately, not as a joint multivariate model. Saved multi-effect evidence feeds gmap(task="coloc") without refitting; the standalone ABF route instead consumes aligned beta/SE summaries directly without LD. For component comparisons, LD is reread only for purity checks.

gbayes() binds native single-trait and multivariate BayesC/BayesR summary regression directly: standardized marginal effects and aligned LD are prepared by gbayes, then fitted using its existing samplers. Parameter learning, pooled posterior summaries and chain diagnostics remain native. Sparse LD can be memory-resident (parallel chains) or disk-backed (serial chains); no dense matrix or retained external pointer is introduced. The R object owns labelled, serializable results. Named trait lists reuse one LD reference; equal sample-size vectors share the same native cross-product object. Alternatively, named study frames/references and an explicit study-to-trait map feed the native multi-provider preparation. Each study retains its own LD operator and local marker map into a checked union; no merged LD matrix is built. Study-specific references require independent errors, including studies mapped to the same trait. Sampling dependence is explicit and separate from latent effect covariance. R checks labels and options; native gbayes owns the multivariate preparation, SPD checks, sampler, covariance/weight updates and posterior summaries. Shared annotation conversion binds native inclusion, pattern, component and variance models; R validates design labels and returns serializable native coefficient summaries and diagnostics. Native gbayes also accumulates requested reference genetic covariance, partition activity/covariance and score uncertainty from joint draws. Group covariance priors are separate from reporting partitions. gscore prepares selected packed targets; no score kernel or sampler is implemented in the R bridge. Scalar residual learning likewise reuses GaussianLearning and its native SSE/variance update, with explicit normalization validated at the R boundary; joint residual scales remain fixed. See the Bayesian regression workflow.

gmap_stat() is R-side input preparation for the native mapping workflow. It reconstructs marginal OLS cross-products from aligned beta/SE/n and phenotype variance. It does not align alleles, infer missing sample sizes or add a native dependency. gmap() retains the preparation provenance. The worked mapping example connects this helper to the existing native fitting and post-fit colocalisation interfaces.

Ownership rules

  • File-format decoding and packed genotype algebra belong to gbits; reusable genomic resource identity, sparse LD, and LD scores belong to gmat.
  • Numerical operators and solvers belong to gsolve; ML/REML model semantics and inference belong to greml.
  • LD-score regression and its uncertainty belong to gcorr, not gmat.
  • Direct multi-score BED application and prepared prediction targets belong to gscore; gbayes owns posterior score accumulation, and gsuite binds the contracts.
  • The gsuite package translates explicit R values into existing public native contracts; it does not reimplement their algorithms.
  • New cross-library dependencies require a demonstrated contract and must follow the existing direction without introducing cycles.

MR through the R interface

gcorr() exposes the native GSMR, GSMR2, IVW, Egger and weighted-median components. Use task="prepare_mr" with aligned trait tables and one LDlist, then task="mr" on the serialized preparation. Selection decisions, HEIDI results, estimate units and method-specific diagnostics remain explicit. Preparation requires matched ancestry and an explicit non-overlapping-sample assertion. Numerical selection/filtering/estimation stays in gcorr; the R layer converts inputs and results. See the MR workflow.

Covariance models through the R interface

gcorr(method="covariance", task="prepare") retains labelled continuous genetic covariance and full joint sampling covariance. gcorr() exposes recursive SEM, descriptive partial-correlation networks and fixed-graph GGM through the existing native gcorr fitter. Parameter tables, trait units and estimation metadata remain explicit. Fitted SEM paths and free GGM edges support native joint Wald tests. Coordinated multivariate GNOVA annotation categories and SumHer architecture components can be fitted with the same model and compared using their full cross-group jackknife covariance; overlapping categories retain their original meaning. See the covariance-model workflow.
