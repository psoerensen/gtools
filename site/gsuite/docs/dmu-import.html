Import a DMU model into YAML

Convert a supported ASCII DMU DIR model and its referenced inputs into a reviewable gsuite analysis.

The development standalone frontend provides gsuite import-dmu. It translates a supported DMU 5.x linear-model specification into the existing YAML interface. The DMU driver file can reference other files, so keep its data, pedigree and parameter files available during conversion. A DMU executable is not required. Existing HPC installations do not gain the command until their frontend is updated; check gsuite --help for import-dmu.

Convert and run

gsuite import-dmu /project/dmu/model.DIR --output /project/converted
gsuite run /project/converted/model.yml

The output directory must be fresh and its parent must exist. Conversion writes:

  • model.yml: the model, natural covariance matrices, execution and outputs.
  • observations.csv and any pedigree_N.csv files: converted input tables.
  • conversion.json: source/output hashes, variable mappings, missing-data counts, original execution controls and translation limits.

Edit execution settings in the YAML as usual. The default is one thread with PARDISO; --threads 8 --sparse-backend pardiso sets the generated requests. The normal gsuite validate, describe and run commands apply afterwards. Conversion checks the generated YAML and inputs; numerical convergence is established only by the subsequent fit. A successful import is not a DMU cross-software qualification.

DMU resolves relative filenames from its working directory. The importer uses the DIR file’s parent by default. If those locations differ, supply:

gsuite import-dmu /project/config/model.DIR \
  --base-directory /project/dmu-run --output /project/converted

Supported initial subset

DMU specification Translation
$ANALYSE task 1 REML with supplied starting covariances, or identity starts when omitted
Tasks 11 / 12 Supplied-covariance solve, using compiled sparse direct / PCG
$DATA ASCII (integers,reals,miss) One combined or two corresponding integer/real files
$VARIABLE Named columns, or generated I1/R1-style names when absent
$MODEL Single/multiple traits, trait-specific fixed classes, overall fixed regressions, independent or correlated random effects across traits
Repeated individual ID in distinct random factors Separate genetic and permanent-environment effects with the same incidence
Zero ABSORB lines Accepted with or without the historical zero lines
$VAR_STR N PED 1 ASCII ... Inbreeding-aware sire/dam pedigree relationship
Default random relationship Independent levels, with trait covariance supplied by $PRIOR
Inline or external $MODEL and $PRIOR Parsed and included in source provenance

Each random factor may occur at most once per trait. The same factor can occur across traits, including with different incidence columns. Covariance entries use factor-local, lower-triangular coordinates in trait order among the traits containing that factor. The residual block follows the last random factor. The importer transfers natural covariances directly. Supplied-covariance solves require every variance diagonal; omitted off-diagonal entries are zero.

DMU integer codes are normalized as integers. Zero classification codes mask the affected trait’s response. Real responses strictly below miss become missing; equality is retained. A missing required fixed covariate on an otherwise observed row is an import error requiring explicit data editing. Original numeric columns and separate masked response columns are retained in the converted CSV.

Data reals default to the documented DMU REAL*4 precision: values are rounded to float32 before writing decimal CSV. For a known double-input setup, --real-precision float64 retains double precision within the documented input range. Covariance parameters are read at double precision. The chosen setting is recorded, and data files are streamed rather than retained as Python tables.

DMU fixed classes use full indicator spaces. The generated YAML represents those spaces through an intercept and treatment contrasts; fixed coefficient references can differ. Compare fitted values and random effects for equivalence. Additional rank deficiencies remain errors in the existing YAML validator; factor merging or model-specific constraints need explicit preparation.

Features requiring further translation

The initial importer rejects nonzero NOCOV, observation weights, nested or random regressions, merged random factors within a trait, binary input, noninbred or phantom-parent pedigree methods, supplied inverse/genomic structures, heterogeneous residual structures, variance restrictions and nonlinear/MCMC directives. In particular, PED 2 is not changed into inbreeding-aware PED 1. An unsupported statistical directive prevents publication of a converted model.

DMU-specific solvers, scaling, preconditioners, stopping and printing controls are recorded separately. They do not select equivalent gsuite algorithms or convergence tolerances. The YAML requests fixed/random estimates, diagnostics and pedigree-based genetic predictions. DMU residual/solution file formats and uncertainty requests are not reproduced by this importer.

The focused tests cover conversion, source preservation, missingness, direct and PCG predictions against independent dense equations, and balanced one-way REML against analytic mean-square estimates. They do not establish agreement with every DMU release or an operational NAV model.

Syntax and input conventions follow the official DMU 5.6 guide. DMU 6 has revised driver keywords and requires a separate import profile.
