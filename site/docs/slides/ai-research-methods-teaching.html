Analysis as a conversation

A scientific question

How much of the variation in body weight is genetic?

My request to the assistant

Check the observations and pedigree. Help specify the model, run it, and examine the diagnostics before making a report.

The work we do together

  1. Check IDs, missingness and study structure
  2. Agree on effects and assumptions
  3. Run a supported model
  4. Examine convergence and results
  5. Save the script and report

Illustrative request. Analysis walkthrough

The question comes first. Whether herd is fixed or random and how to handle repeated records depends on the study. The assistant should explain its proposals and keep data changes visible. The final script and report make the analysis reproducible beyond the conversation.

Explicit models beneath the conversation

A short gsuite specification

fit <- gfit(
  formula = BW ~ sex + cohort + herd +
    (1 | id),
  data = data,
  pedigree = pedigree,
  task = "reml"
)

data and pedigree are ordinary R data frames.

The qgtools approach

  • Formula: which effects?
  • IDs: which observations and animals?
  • Kernel: which relationships?
  • Covariance: which variance components?
  • Task: what should be estimated?

The short and explicit forms describe the same supported model.

Complete example and explicit covariance components

This example assumes the tutorial data have already been prepared. The model contains fixed sex, cohort and herd effects, a pedigree animal effect and an independent residual. Omitted starts use the existing gsuite initializers. The general model language is valuable for humans and assistants, but it does not establish numerical support for every model it can describe.

A focused computational foundation

Two public R packages

gsuite for analysis. gsim for simulation.

Libraries Responsibility
greml, gcorr, gscore Mixed models, genetic correlation and scoring
gsolve, gmat, gbits Solvers, genomic matrices and packed genotype operations

gsuite currently exposes selected native capabilities.

The aim is to reuse good components and keep their responsibilities clear.

Responsibilities and current dependencies

This is a map of responsibilities, not a build dependency graph. gsim is a simulation package in its own right. gscore belongs to the ecosystem even though its current implementation is standalone. We do not need to build a conversational system inside the R package. Clear interfaces and structured results let an assistant work with the software.

When the analysis needs something new

I have repeated measurements. Can we separate genetic effects from persistent environmental differences between animals?

First check what already exists. Repeatability routes are already in the ecosystem.

If something is missing The next step
An R interface Expose an existing capability
A model combination Connect existing components
Numerical machinery Implement it in the owning library

We add the missing piece, then make it reusable.

Model development walkthrough

A limitation in one convenience interface does not mean that the numerical engine is missing. The assistant should inspect the catalog, code and evidence before suggesting development. If the model already has a suitable route, use it. If a gap remains, define the statistical contract before implementation.

From running code to supported models

Code that runs becomes a supported model only after its statistical meaning and numerical behavior have been checked.

Statistical meaning

  • Does the code represent the intended model?
  • Can the data distinguish its components?
  • Are assumptions and limitations explicit?

Numerical behavior

  • Compare with a small independent reference
  • Check estimates, predictions and convergence
  • Test failures and affected existing workflows

Two wrappers over the same engine are useful for integration checks, but they are not independent numerical validation. Choose tolerances and pass criteria before interpreting results. Small examples do not qualify large workloads or other platforms. Record support for the exact model, backend and inference combination. AI helps assemble this evidence; it does not replace it.

Evidence: gsuite versus DMU

Three frozen pedigree models

50,000 animals

gsuite 0.29.0 and DMU 5.6

Maximum covariance-estimate difference below \(4.3\times10^{-8}\).

Prediction correlations above 0.999999999998 on the predeclared 1,000-animal subset.

Competitive runtime on these tested models. Each time is one execution: gsuite fit versus the DMU preprocessing and fitting pipeline.

Results, scope and provenance

The numerical results provide evidence for these frozen direct pedigree REML models. The covariance agreement is across the saved parameters. Prediction comparisons use the predeclared first 1,000 pedigree-coded animals, not all 50,000. Likelihood constants remain unreconciled. Timings are descriptive single runs with different work boundaries, so this is not a general speed claim or qualification of all current gsuite routes.

How can we organize our expertise so that progress in one project benefits the whole programme?

This is the direction I would like us to discuss. Applied researchers, statisticians and software developers bring different knowledge. AI can help with the work between them, but common interfaces, review and evidence are still needed. We can start with a bounded problem rather than a large new system.
